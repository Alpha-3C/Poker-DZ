# 《叫主》项目学习笔记

这份笔记记录我在 Poker-DZ 中实践的 Unity 与 C# 设计方法。内容以当前仓库的**实际运行路径**为准；规则说明见[玩法文档](扑克-叫主.md)，类与场景的索引见[项目结构整理](项目结构整理.md)。项目使用 Unity 2022.3.62f1c1，核心是一名人类玩家与三名 AI 的四人单机牌局。

## 1. 从完整的一轮游戏理解职责划分

一轮游戏要处理准备、发牌、叫分、庄家拿底牌、选主与弃牌、12 墩出牌和结算。如果把所有逻辑堆在一个脚本里，按钮回调、游戏规则和显示更新会互相交织。项目采用了一个较轻量的 **Manager of Managers** 思路：

- `GameFlowController` 是最高层的流程编排者，持有四个阶段管理器的场景引用，也保存跨阶段共享的配置与结果，例如叫分、庄家索引、主花色和闲家得分。
- `RoundManagement` 负责准备、发牌和一轮结束后的胜负结算。
- `BiddingManagement` 负责叫分轮转、最高分、Pass、超时和庄家确定。
- `KittySelectionManagement` 负责底牌加入庄家手牌、选主和弃牌。
- `PlayPhaseManagement` 负责 12 墩出牌、合法性检查、墩赢家和得分累加。
- `GameStateMachine` 保存并广播当前阶段；`CardManagement`、`PlayerManagement` 管理牌与玩家数据；UI 脚本处理交互和展示。

这不是一个通用框架，而是围绕本游戏阶段划分的具体组织方式。它让我学会让上层只决定“下一步做什么”，让阶段管理器决定“这一步如何完成”。阅读入口是 `GameFlowController.StartGame()` → `RunGameLoop()` → `RunOneRound()`；沿着这条调用链可以追踪全部主要玩法。

### 一轮运行的主干

```text
场景 StartButton → GameFlowController.StartGame()
  → ReadyPhase()
  → DealPhase()
  → RunBiddingCoroutine() ── 全员 Pass 时重新发牌并重试
  → RunKittySelectionCoroutine()
  → PlayAllTricksCoroutine() ── 12 墩
  → RoundEndCoroutine()
  → 下一轮（目前没有整场结束条件）
```

`GameFlowController` 通过 Inspector 引用阶段管理器，而阶段管理器在 `Start()` 中获取若干共享管理器。这个安排让主流程代码保持简短，但也意味着场景中的引用配置是运行前提。新增阶段时，需要同时检查场景绑定、状态切换、UI 激活和数据归属。

## 2. Manager 单例与 Unity 生命周期

`GameFlowController`、`GameStateMachine`、`PlayerManagement`、`CardManagement` 都提供静态 `Instance`。它们在 `Awake()` 中注册自己，其他脚本通常在 `Start()` 中读取实例；其中多处使用 `DontDestroyOnLoad(gameObject)`。我由此理解了 Unity 的 `Awake`/`Start` 顺序如何帮助场景内对象建立依赖：先创建共享对象，再由使用者取引用。

这些单例目前是**场景级便捷入口**，不等于所有 `*Management` 脚本都是单例。叫分、底牌、出牌、轮次管理器由 `GameFlowController` 持有组件引用，UI 也经常通过 `GetComponent` 与同一物体上的阶段管理器配合。

单例的收益是阶段脚本可以直接取得公共数据，不必层层传参；代价是依赖被隐藏在静态字段里，测试和多场景切换会更敏感。当前工程主要在一个场景中运行。以后扩展多场景时，要特别检查重复实例处理、静态事件解绑与 `DontDestroyOnLoad` 对场景 UI 引用的影响。源码中 `GameStateMachine` 的重复实例分支调用了 `Destroy(Instance)`，与其他单例销毁新对象的做法不同，值得在扩展前修正；`CardManagement` 的重复实例分支也没有显式销毁新对象。

## 3. 状态机和流程控制器各自解决什么问题

`GameStateMachine` 定义 `Setup`、`Dealing`、`Bidding`、`KittySelection`、`Playing`、`TrickEnd`、`RoundEnd`、`GameEnd` 等状态。`ChangeGameState()` 更新 `gameState`、输出状态变化日志，并触发静态事件 `OnGameStateChanged`。

当前运行路径中的主要状态顺序是：

| 状态 | 谁切换到此状态 | 当前作用 |
| --- | --- | --- |
| `Setup` | 初始化和 `RoundManagement` | 准备/下一轮开始 |
| `Dealing` | `RoundManagement.DealPhase` | 发牌后标记当前阶段 |
| `Bidding` | `BiddingManagement` | 叫分中 |
| `KittySelection` | `KittySelectionManagement` | 选主与弃牌中；`Slot` 据此发弃牌选择事件 |
| `Playing` | `KittySelectionManagement` | 出牌中；`Slot` 和 `PlayPhaseUI` 据此处理点击 |
| `RoundEnd` | `PlayPhaseManagement` | 12 墩结束，随后执行结算 |

`RunOneRound()` 使用协程直接串联阶段，所以**流程控制器负责推进阶段，状态机负责记录和通知状态**。当前活跃代码中没有订阅 `OnGameStateChanged` 的组件；已有 UI 主要读取 `gameState` 判断交互，或通过 `GameEvents` 收到局部更新。`TrickEnd` 尚未在活跃流程中切入；`GameEnd` 的路径存在，但 `CheckGameEndCondition()` 目前固定返回 `false`，所以会持续进入下一轮。这些细节避免把“已声明的状态/事件”和“已经运行的功能”混为一谈。

我在这里学到：状态枚举本身不会驱动流程。需要明确谁有权切换状态、谁负责等待阶段完成、谁使用状态约束输入。若以后把每墩结算做成独立状态，就应让 `TrickEnd` 有真实切换与退出路径，而不只是枚举值。

## 4. 协程如何串起人类操作与 AI 操作

这个项目的“异步”主要指 **Unity 协程在主线程上分帧等待**，不是 `async/await` 或后台并行计算。上层 `yield return StartCoroutine(阶段协程)`，确保前一阶段结束后再进入下一阶段；阶段内部用 `WaitForSeconds` 展示过程、模拟 AI 思考，用 `yield return null` 或 `WaitUntil` 等待玩家输入。

三个典型例子：

1. **准备**：`RoundManagement.WaitForAllReady()` 逐个让 AI 显示准备状态，再给人类玩家的准备按钮绑定一次性回调；每帧检查四人是否都准备好。
2. **叫分**：`BiddingManagement.RunBiddingCoroutine()` 在 AI 回合等待 `aiThinkTime`，在人类回合打开 `BiddingUI` 并等待确认、Pass 或计时超时。超时会自动 Pass。全员 Pass 时，外层流程重新发牌并再次运行叫分阶段。
3. **出牌**：`PlayPhaseManagement.WaitForHumanPlayCoroutine()` 等待 `OnHumanCardSelected()` 将合法牌写入 `selectedCardByHuman`；AI 回合等待一个随机的展示时间后调用 `IAIPlayer.DecidePlayCard()`。这个等待时间不等于 AI 算法在后台运行。

协程让“一轮游戏”的代码看起来像顺序叙事，同时保留 UI 响应。使用时需要防止重复启动同一个游戏循环，也要考虑组件停用或场景切换时等待条件永远无法满足。目前 `StartGame()` 可再次调用而没有防重入标记，属于后续可加强的生命周期管理。

## 5. 事件系统：把逻辑变化传给显示层

项目有两类事件：`GameStateMachine.OnGameStateChanged` 代表全局状态变化；`GameEvents` 是静态事件集合，服务于手牌槽位与交互。活跃代码主要使用后者，包括 `OnSlotCardsChanged`、`OnSlotButtonsActivated`、`OnSlotButtonsEnabled`、`OnDiscardsCleared`、`OnDiscardSelected` 和 `OnCardSelectedInPlaying`。

一次“人类玩家选牌出牌”的消息链是：

```text
Slot.OnCardSlotClicked()
  → GameEvents.TriggerCardSelectedInPlaying(card, slotObj, isSelected)
  → PlayPhaseUI.HandleCardSelectedInPlaying() 更新选中态和确认按钮
  → 玩家点击确认按钮
  → PlayPhaseManagement.OnHumanCardSelected() 校验合法性
  → 等待中的协程继续，移除手牌并更新桌面
  → GameEvents.TriggerSlotCardsChanged(playerIndex)
  → DeskUI.HandleSlotCardsChanged() 刷新对应座位的槽位
```

弃牌选择也从 `Slot` 发出事件，由 `KittySelectionManagement` 收集选中牌；确认数量是否等于 6 后才进入下一步。`DeskUI`、`PlayPhaseUI` 等在 `OnEnable()` 订阅，在 `OnDisable()` 取消订阅，避免对象停用后继续响应。事件把“牌已变化”和“怎样重新绘制手牌”分开了；同时我也看到静态事件需要严格管理订阅生命周期，否则容易产生重复响应或失效引用。

`GameEvents` 是进程内消息分发，没有持久化、排队或跨线程保证；事件触发后订阅者在当前调用栈同步执行。它适合 UI 通知，复杂的游戏规则校验仍应由阶段管理器或规则函数承担。

## 6. 扑克牌规则数据与比较器的拆分

`Card` 保存花色、点数、是否 Joker 和贴图索引；`CardManagement` 创建 54 张牌、洗牌、发牌、加载卡面资源与整理手牌；`Player` 保存座位、队伍、AI 策略和手牌。规则和显示尽量分开：`CardData` 管理卡牌图片，`Slot` 管理点击与选中动画，`DeskUI` 将玩家手牌投影到 UI。

比较牌大小时必须区分两个问题：

- **手牌排序**：`CardComparer.SuitCompare()` 把 Joker、2、主花色、其他花色分组，供 `CardManagement.SortHands()` 展示手牌，也被简单 AI 的出牌选择使用。
- **一墩赢家**：`CardComparer.TrickCompare()` 使用首出花色与主花色比较墩内牌。`PlayPhaseManagement.DetermineTrickWinnerIndex()` 遍历本墩四张牌，并通过 `playOrder` 把“在本墩的第几张”映射回玩家座位。

合法出牌是第三个独立问题，由 `CardManagement.CanDealCard()` 判断。首出为主花色时，主花色普通牌、2、Joker 都算应跟牌；首出为副花色时，只有该副花色普通牌算应跟牌。UI 用这条规则禁用不能出的牌，`PlayPhaseManagement.OnHumanCardSelected()` 再做一次校验；AI 策略也先筛选合法牌。这体现了“UI 提示”和“规则校验”应共同使用同一个判断入口。

每墩结束时，只有闲家获胜才累计该墩中的分牌：5 算 5 分，10 和 K 各算 10 分。12 墩结束后把闲家总分与最后一墩赢家写回 `GameFlowController`；`RoundManagement` 再按“叫分 + 闲家得分 > 100，或最后一墩由闲家获胜”判定本轮获胜阵营。

## 7. 用 `IAIPlayer` 接入可替换策略

`IAIPlayer` 规定准备、叫分、选主、弃牌、出牌等决策入口。`PlayerManagement.InitializePlayers()` 创建玩家时把具体策略对象放入 `Player.aiPlayer`；当前 0 号座位是人类，1、3 号座位使用 `AdvancedAIPlayer`，2 号座位使用 `BasicAIPlayer`。各阶段只调用接口，不需要知道具体策略类。

`BasicAIPlayer` 的核心出牌行为是**规则过滤 + 贪心选择**：先列出可以出的牌，再按 `SuitCompare` 排序，取比较器意义下最小的合法牌。给定相同的手牌顺序与局面，这一步没有随机抽牌，容易解释和复现。其弃牌策略按普通小牌、非主花色的大牌、主牌的类别依次取牌。选主偏向张数最多的普通花色。

但“基础 AI 完全确定性”并不准确：`DecideBid()` 在符合叫分阈值时随机选择可叫分数；`DecideTrumpSuit()` 遇到花色张数并列时随机选择。`AdvancedAIPlayer` 的叫分使用随机概率，出牌则参考当前领先方、己方阵营与可压过当前最大牌的候选牌。它没有搜索树、机器学习训练或长期记牌；`UpdateMemory()` 与 `EvaluateSituation()` 当前还是占位实现。准备阶段也尚未调用接口里的 `IsReady()`，而是根据 `Player.IsAI` 自动标记准备。

我在这里学到的是**先定义策略接口，再逐步提高决策质量**：阶段代码保持稳定，策略可以从最小合法牌发展到考虑得分、队友、已出牌和概率的算法。下一步若希望进行可复现的 AI 对比，应把随机数源注入策略、记录种子，并为相同局面建立测试用例。

## 8. 当前边界与下一步学习方向

以下是阅读当前源码得出的实现边界，属于后续改进记录，不代表已做运行时故障复现：

- **整场结束**：`CheckGameEndCondition()` 固定返回 `false`；目前实现的是反复进行的一轮轮游戏，而非有总积分终点的整场比赛。
- **状态事件**：`OnGameStateChanged` 已发布但活跃代码未订阅；`TrickEnd` 枚举暂未使用。若需要回放、动画或音效，可以沿此通道扩展。
- **全员 Pass 重发牌**：`DealPhase()` 会再次发牌，但 `KittyCards` 的清空只在新一轮 `ReadyPhase()` 中进行；同一轮因全员 Pass 重发时应先清理旧底牌。
- **规则参数化**：出牌阶段将 12 墩写成固定循环，准备数组也按 4 人分配。若想真正支持可配置人数或手牌张数，需要统一从配置派生。
- **AI 行为检查**：`AdvancedAIPlayer` 中局数变量由“当前墩已出牌张数 / 4 + 1”计算，而当前墩最多只有 3 张先出牌，实际无法表示跨墩进度；应由出牌阶段传入真实墩号。
- **构建兼容性**：`CardManagement.cs`、`Slot.cs` 引入了 `UnityEditor` 命名空间；目前主要在编辑器 Play 模式使用，若日后制作独立构建，应检查并移除运行时代码对编辑器 API 的依赖。
- **验证方式**：基本玩法、状态机、流程和牌力比较已有作者手动验证；尚无覆盖特殊牌、全员 Pass、断开 UI 引用或重复启动的自动化测试。后续可优先把纯规则函数提取成易测单元。

这些边界提醒我：架构名称只是起点，真正重要的是对象生命周期、数据归属、异常路径和可验证性。当前项目已经让我把管理器协作、状态记录、事件通知、协程等待与 AI 策略接口放进一条完整的游戏流程中；后续迭代可以围绕这些具体边界逐步加强。
